#                                                           SQLSphere

SQLSphere is a web-based AI database assistant that lets users query a MySQL database using normal English instead of writing SQL manually.

This project was developed as a major project to explore the use of Generative AI with databases. The main idea was to make database querying easier while still showing the SQL generated by the AI and keeping control over what actually gets executed.

## What does it do?

Normally, if I want to find students whose CGPA is greater than 8, I would have to write something like:

```sql
SELECT * FROM students WHERE cgpa > 8;
```

With SQLSphere, the user can simply type:

```text
Show students with CGPA above 8
```

The question is sent to the Flask backend, Gemini generates the SQL based on the database schema, the SQL is validated and then executed on MySQL. The result is sent back to the React frontend.

The generated SQL is also shown in the dashboard so the user can see what the system actually executed.

## How the project works

The basic flow is:

```text
User
 ↓
React Dashboard
 ↓
Flask API
 ↓
Value Grounding + Conversation Context
 ↓
Gemini
 ↓
Generated SQL
 ↓
SQL Validation
 ↓
MySQL
 ↓
Results
```

There are a few extra steps around this flow for things like query repair, history and evaluation.

## Features

### Natural language queries

The main feature is converting normal questions into SQL.

Some examples:

```text
Show all students

Show students with CGPA above 8

Show students from CSE

Show students with attendance below 75 percent

Show the average CGPA of students in each department
```

The system uses the current database schema when generating the query.

### Value grounding

One problem with Text-to-SQL is that the words used by a user don't always exactly match the values stored in the database.

For example, the database contains:

```text
Computer Science and Engineering
```

A user might type:

```text
Show students from CSE
```

SQLSphere checks the actual database values and can map:

```text
CSE → Computer Science and Engineering
```

The same idea works for phrases such as:

```text
Computer Science → Computer Science and Engineering
```

The system also checks for ambiguity. For example, if the user asks:

```text
Show students from the engineering department
```

and several department names contain "Engineering", the system should ask the user which department they mean instead of making an arbitrary choice.

### Conversation context

The application keeps a small amount of recent query context so that follow-up questions can be understood.

For example:

```text
Show students with CGPA above 8
```

followed by:

```text
Now show only their names
```

The second query can use the condition from the first query.

### SQL security

Generated SQL is not executed directly without validation.

SQLSphere only allows read-oriented queries and blocks operations such as:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
CREATE
TRUNCATE
```

It also rejects multiple SQL statements and SQL comments.

For example, a query such as:

```sql
DROP TABLE students;
```

will be rejected by the backend.

### Query repair

Sometimes an AI-generated query can contain an SQL error.

SQLSphere has a query repair step for these cases. When an execution error occurs, the failed SQL can be sent back to Gemini for correction. The repaired SQL is then validated again before it is executed.

The dashboard also shows when a query has been automatically repaired.

### Query history

Previous queries are kept in the application so they can be viewed again.

The history section allows the user to:

- see previous questions
- view the generated SQL
- run a previous query again

### SQL explanation

The application can explain the generated SQL in simpler terms.

This is useful when the user wants to understand what the generated query is doing instead of just looking at the SQL syntax.

### Database schema explorer

The dashboard contains a schema explorer that reads the database structure and displays the tables, columns, data types and relationships.

The current database contains:

```text
students
departments
faculty
courses
enrollments
marks
attendance
```

### Charts

Depending on the returned data, SQLSphere can display the results as:

- Bar chart
- Line chart
- Pie chart
- Doughnut chart

### Exporting results

The results can be exported from the dashboard as:

- CSV
- Excel
- PDF

### Evaluation data

During development, the backend records information about queries so that the Text-to-SQL system can be evaluated.

The recorded information includes things such as:

```text
Question
Generated SQL
Grounded values
Confidence score
Validation result
Execution result
Row count
Repair attempts
Final SQL
Response time
Context usage
```

This was useful while testing the different parts of the system.

## Running the project

### 1. Clone the repository

```bash
git clone https://github.com/YOUR_USERNAME/SQLSphere.git
cd SQLSphere
```

### 2. Set up MySQL

Create the database:

```sql
CREATE DATABASE student_management;
```

Import the required tables and sample data.

### 3. Backend setup

Go to the backend directory:

```bash
cd backend
```

Create a `.env` file:

```env
MYSQL_HOST=localhost
MYSQL_USER=root
MYSQL_PASSWORD=your_mysql_password
MYSQL_DATABASE=student_management
GEMINI_API_KEY=your_gemini_api_key
```

Install the required packages:

```bash
pip install flask flask-cors mysql-connector-python python-dotenv google-genai
```

Start the backend:

```bash
python app.py
```

The backend runs on:

```text
http://127.0.0.1:5000
```

### 4. Frontend setup

Open another terminal and go to the frontend:

```bash
cd frontend
npm install
npm start
```

The React application will normally be available at:

```text
http://localhost:3000
```

## Current limitations

This is a project built around a specific MySQL database, so the quality of the generated SQL depends partly on the database schema and the information available to Gemini.

The value grounding system also has to deal with cases where a user's wording can refer to more than one database value. In those situations, the application is designed to ask for clarification rather than guess.

The current conversation history and evaluation data are maintained by the backend and are not intended to be a full persistent multi-user history system.
